# /dev-flows:configure

Record this repository's dev configuration in `.agent-flows/config.json` at the repo root: settings every flow relies on (like the base branch) and the integrations the repo uses, with the ids flows need to reach them. Other dev-flows commands read it instead of guessing or asking every time. The file is committed and shared with the team, so it holds **configuration only**: ids, slugs, branch names. No secrets, and nothing that points at one.

Flows never ask for a vendor. They ask for a **capability**, and use every integration the repo configured for it:

| Capability | Name | Used for | Integrations | Levels (`use`) |
|---|---|---|---|---|
| `sourceControl` | Source control | The hosted repository: pull requests, CI checks, code review | GitHub, GitLab | `read`: Read pull requests (evaluate); `write` (default): Also push branches, open and edit draft pull requests (sync), mark them ready, resolve review threads (ready), and merge them (finish) |
| `codeReview` | Code review on request | An automated reviewer that reviews a pull request when asked (ready) | Claude Code (GitHub Actions) | `request` (default): Request a review only when a ready run asks for one (`--review`); `every`: Request one on every ready run, unless it says `--no-review` |
| `stacking` | Stacked PRs | Stacked branches and pull requests on top of source control | GitHub, Graphite | used or not |
| `issueTracker` | Issue tracker | Tickets: link branches and PRs, file and close issues | GitHub, Linear, Jira | `link` (default): Find a branch's existing issue and link it from the PR; `track`: Also file an issue for every branch, and keep its status and state in step (sync) |
| `workspaces` | Workspaces | Open a branch in a workspace of its own, with a coding agent already working on it | Superset, Orca, Conductor, Git worktrees | used or not |
| `browser` | Browser | A browser built into the workspace app, for opening a branch's preview next to its agent (preview) | Superset, Orca | used or not |
| `deployments` | Deployments | Preview and production deployments, runtime logs | GitHub, Vercel | used or not |
| `database` | Database | Database branches per worktree, migrations | Neon | used or not |
| `errorTracking` | Error tracking | Production errors behind a bug | Sentry | `link` (default): Link the errors a branch fixes from its PR; `resolve`: Also resolve them when the PR merges (sync) |
| `sessions` | Session sharing | Share the agent session behind a change, linked from its PR and issue | Lore | used or not |
| `analytics` | Product analytics | Usage events, funnels, session replay | PostHog | used or not |
| `featureFlags` | Feature flags | Gated rollouts and experiments | PostHog | used or not |
| `chat` | Team chat | Where dev flows post announcements and alerts | Slack | used or not |

A repo can configure any number of integrations for a capability (none, one, or several, like Linear for product work and Jira for support tickets), and flows use all of them. An integration can provide more than one capability, and most can be configured more than once (one Vercel project per app in a monorepo): the entry is then a list of instances, each with a unique `name`:

```json
"vercel": [
  { "name": "web", "project": "prj_web", "directory": "apps/web" },
  { "name": "docs", "project": "prj_docs", "directory": "apps/docs" }
]
```

The file is made of **sections**, each an object of fields at a dotted path. Every section but `repo`, `sync`, `ready`, `finish`, `cancel`, and `hooks` is an integration:

| Section | Name | Provides | Used for | Fields | Reached through | Look up with |
|---|---|---|---|---|---|---|
| `repo` | Repository (always) |  | The branch work merges into, for diffs, reviews, and PRs | `baseBranch` (required): Branch feature work merges into; `protectedBranches` [string[]]: Branches besides the base that no flow works on directly, such as a production branch the base is promoted to: sync, ready, finish, and cancel refuse on them |  | `git symbolic-ref --short refs/remotes/origin/HEAD`, or ask. Set `protectedBranches` only when the agent instructions name a branch work must never land on directly (a production branch the base is promoted to) |
| `sync` | Sync format |  | How sync writes the PR body, its title, and the issue's link lines; unset, it uses its own format | `linkLabels`: Label link lines by capability (`> Issue:`, `> Errors:`, the default) or by integration name (`> Linear:`, `> Sentry:`); `errorVerb`: Word that starts each error line (`Fixes`); `prTitle`: PR title template: `{issueId}` and `{title}` are the issue's, `{summary}` a summary of the change in the repo's title convention; unset, the repo's convention; `linkStyle`: How the PR body's issue line links the issue: `link` (the default: `[<ID>](<URL>) <title>`) or `url` (the issue's bare URL, `Issue: https://...`); `timezone`: IANA time zone the team reads the last-synced line's time in (default `UTC`), shown by its short name (`PT` for `America/Los_Angeles`). The team's zone, never just your machine's; `quoteLinks` [boolean]: Write the PR body's link lines as quotes (`> Issue:`, the default); false writes them plain (`Issue:`). The issue's own lines stay quoted; `prSections` [string[]]: The headings of sync's sections in the PR body, in order, in place of the repo's PR template or Summary and Test plan; `blockMarkers` [boolean]: Wrap sync's part of the PR body in HTML comment markers (default true); false bounds it by the link lines and the last-synced line instead; `prLinkLine` [boolean]: Write the issue tracker's link line (`Fixes <ID>`, `Part of <ID>`) in the PR body when its `prLink` op puts one there (default true); false leaves it out, for a repo whose tracker links by the issue line or the title alone; `noIssueLine`: With no issue, still write the issue line, with this after its label (`Linear: none`); unset leaves the line out; `footer` [boolean]: End sync's part of the PR body with the last-synced line (default true). False leaves it out, only with `blockMarkers` on: without markers, that line is where sync's part ends, so it's always written; `commitBodies` [boolean]: Read each commit's whole message, not only its subject, when writing the PR body (default false), for a repo whose commits carry notes the PR draws on (a `Verification:` section); `linkUnverified` [boolean]: When an issue ref the branch, PR title, argument, or an adopted tool's state names can't be loaded from an issue tracker at `link` (a token or MCP server for another workspace, an outage), link it anyway, marked unverified in the report, instead of linking none (default false); `requireBase` [boolean]: Stop when the pull request targets neither `repo.baseBranch` nor the branch's stack parent, as finish does (default false: sync catches up to whatever base the pull request has); `adoptState` [string[]]: Another sync tool's per-branch state files, read once for a branch sync hasn't synced (after bitfab-dev's own), for the issue it linked: JSON with `branch` and `linearId` or `issueId`. `{gitDir}` and `{gitCommonDir}` are the worktree's git dirs; other paths are relative to the worktree root; `adoptHeader`: A regular expression for the link lines another sync tool puts on top of a PR body (`^Linear\s*:`). A body that starts with one is that tool's: sync replaces those lines and its sections of the same names as sync's own, instead of adding its block above them |  | Leave it out for sync's own format. A team that also runs bitfab-dev's sync uses its format, so the two don't duplicate each other's lines. A team moving from another sync tool sets `adoptState` and `adoptHeader` to that tool's state file and PR header, and the format fields to what it wrote, so sync takes its branches over without a second copy of each line. Set `commitBodies` when the repo's commit messages carry verification notes, `requireBase` when the host's default branch isn't the base (a pull request opened by hand would target it), and `linkUnverified` when the issue tracker is linked only and its issues may be out of reach |
| `tickets` | Ticket rules |  | How the team files and ranks issues, beyond what any one tracker holds: the planning document, the blocker mark, and the rules create-tickets checks before filing | `planningDoc` [boolean]: Record each create-tickets run's notes, and the issues filed from them, in the planning document of the cycle they're filed in, and link each issue back to it with a `> Planning:` line; `blockerMark`: Mark at the start of the title of an issue that stops a customer: create-tickets adds it to an item marked `blocker`, sync keeps it when it retitles, and tickets-to-work takes marked issues first within each priority; `dueDateRequired` [string[]]: Priorities (`urgent`, `high`, `medium`, `low`, `none`, on the tracker's scale) whose issues must have a due date: create-tickets won't file one without it, unless the issue is a parent whose sub-issues carry the dates, and sync asks for one when it files or ranks the branch's issue at one of them; `ranks` [string[]]: The team's names for the tracker's priorities, one each for `urgent`, `high`, `medium`, `low`, and `none`, in that order (default `Urgent`, `High`, `Medium`, `Low`, `No priority`): start-work's `--section-by-rank` names sections after them, tickets-to-work shows them and takes them in `--priority`, and create-tickets takes them as an item's priority and shows them beside it; `estimateScale` [number[]]: The estimates the team sizes work in, smallest first: sync and create-tickets estimate on it, and create-tickets refuses an estimate off it; `parentFollowsSubIssues` [boolean]: A parent issue takes the priority of its most urgent open sub-issue, and, when it has no cycle, the cycle of its earliest one; `assignOnSync` [boolean]: Sync assigns the branch's issue to the person running it on every remote pass, not only when it files the issue (default false: sync never reassigns); `timezone`: IANA time zone the team plans in, for what "today" is when create-tickets checks due dates and dates planning sections (default: this machine's). Set it only for a team that works in one zone, never from your own machine's |  | Leave it out unless the repo's agent instructions say how the team ranks and files work: a planning document per cycle, a mark for customer blockers, due dates required at some priorities, its own names for the priorities (P0, P1, …, read off the doc that maps them to the tracker's), parents ranked by their sub-issues, the estimates the team sizes work in |
| `ready` | Ready checks |  | The commands ready runs before it publishes a branch (unset, it runs the scripts of each package the branch touches), the steps it skips, the CI checks it ignores or waits for, how long and how many times it waits on CI, and the repo's own hooks at its steps | `fix` [string[]]: Commands that fix the tree in place (formatters, lint autofixes, code generators), run in order from the repo root before the checks. `{base}` is the branch's merge base; `{files}` the changed files that still exist (shell-quoted), and `{files:<glob>}` those matching a glob (one without a `/` matches the file name: `{files:*.py}`); a command whose `{files}` matches none is left out; `checks` [string[]]: Commands that verify the branch (lint, type checks, the tests it touches, a build), run in order from the repo root; none of them may deploy, publish, migrate, or write to a shared service. `{base}` and `{files}` as for `fix`; `skip` [string[]]: Steps ready skips on every run: `cleanup` (what must change with the branch), `tests` (writing tests for new behavior), `fix` and `checks` (the local fix and check commands, before the first push and before every CI fix push), `local` (all four), `ci` (waiting on CI and fixing it), `reviews` (automated reviewers' threads), `all` (every step: ready only commits, publishes, and syncs). A run's `--skip` adds to these; `ignoreChecks` [string[]]: CI check names ready neither waits on nor fixes, such as preview deploys or optional coverage. `*` matches any run of characters, case aside. A run's `--ignore-check` adds to these; `tests`: Command that runs the tests the branch touches, from the repo root, after the checks; `{tests}` is the test files ready picks (shell-quoted), and a run with none skips it. It runs even with `checks` set, which otherwise replace ready's related-tests step. `{base}` and `{files}` as for `fix`; `requiredChecks` [string[]]: CI check names ready and finish wait for until they report: a check named here and not on the commit yet counts as pending, so a quick check settling first can't read as the whole run. For a check that gathers the others and starts late, or one the host's branch rules don't mark required. `*` matches any run of characters, case aside; `ciTimeout` [number]: Minutes ready waits for a pushed commit's checks to settle (default 15); `maxPasses` [number]: The most CI passes one `loop` run makes: on the last one it waits and reports, and pushes no more fixes (default: no cap; loop stops when a fix doesn't work or CI is green); `settleGrace` [number]: Seconds the set of CI checks and their states must hold still, once none is pending, before ready and finish take the run as settled, so a check that registers a moment after the others finish isn't missed (default 0: settled as soon as none is pending); `requireChecks` [boolean]: Never take a commit with no CI checks (or only ignored or optional ones) as having no CI: ready and finish wait until one reports, and a pass with none times out instead of passing (default false: none within 3 minutes reads as no CI); `rollupChecks` [string[]]: CI checks that only gather the others' results (`tests-passed`, `ci-required`): ready never fixes one itself, but works the failing checks it rolls up, and a rollup failing with nothing else failed stops for the user. `*` matches any run of characters, case aside; `before` [hook[]]: Once ready has scoped the branch, before its local cleanup: for what CI enforces that no integration covers (a version bump, a release collision, a migration check), and rules for when certain paths change. Commands may change the checkout, but not deploy, publish, migrate, or write to a shared service or database. A failure stops the command.; `beforePublish` [hook[]]: After ready's local cleanup and checks, before it commits and pushes: what the files to publish need last (regenerated screenshots). What hooks change is committed with the rest. Commands may change the checkout, but not deploy, publish, migrate, or write to a shared service or database. A failure stops the command.; `beforePush` [hook[]]: After ready's local sync has committed the branch, before it pushes: for a check that reads committed history (a scan of the commits about to publish). Ready commits what hooks change, with the repo's convention for the message, before it pushes. Commands may change the checkout, but not deploy, publish, migrate, or write to a shared service or database. A failure stops the command.; `beforeFixPush` [hook[]]: In ready's CI step, after each batch of CI fixes is committed, before it's pushed: the checks `beforePush` runs, for the fix pushes it doesn't see. Ready commits what hooks change, with the repo's convention for the message, before it pushes. Commands may change the checkout, but not deploy, publish, migrate, or write to a shared service or database. A failure stops the command.; `after` [hook[]]: At the end of ready, finished or stopped, just before its report. Commands may have side effects outside the checkout; ready's work is published by then. A failure is reported, and the rest still run. |  | Leave it out to run each touched package's own scripts and every step, and to wait on every CI check. Set `fix` and `checks` when the repo has one command for the whole check (`bun run validate`), or its own script that picks the checks a branch needs; detection proposes them from a root `validate`, `check`, `verify`, or `ci` script that chains others and runs nothing unsafe, its fix scripts, and, when that script runs no tests, the changed-tests command of the runner the root depends on, its test script runs, or a tracked runner config (`vitest.config.ts`) sets up, since `checks` replaces ready's own related-tests step; for a Python repo with no such script, detection proposes Ruff (else Black and Flake8) on `{files:*.py}`, and `pytest {tests}` as `tests`, through `uv run` or `poetry run` when that lockfile is tracked; `tests` when the repo's runner takes test files and the checks shouldn't pick them; `skip` and `ignoreChecks` when the team never wants a step, or a check is slow or optional (a preview deploy); `requiredChecks` for a check merging needs that may report late (one that gathers the others, like `tests-passed`); `ciTimeout` when CI takes longer than 15 minutes; `maxPasses` to bound a `loop` run; `settleGrace` when a check registers only after the others finish; `requireChecks` when every commit runs CI, so no checks means something's wrong; `rollupChecks` for a check that only gathers the others; `before` for a check CI runs that ready would otherwise find only after pushing (a version bump), or a rule that applies only when certain paths change; `beforePublish` and `after` for the repo's own steps at those points; `beforePush` for a check of the commits about to publish, and `beforeFixPush` for the same check on CI fix pushes |
| `evaluate` | Evaluate |  | Whether evaluate records its verdict for finish to gate on, how much of a branch it reviews again, who judges and by which of the repo's rules, what it runs first (a fetch, the repo's scan, the tests), and what stops a merge | `record` [boolean]: Record each evaluation of the current branch's committed, pushed head: its verdict (`pass` for Ship, `flag` for Address first, `stop` for Rethink), its findings, and each file's change, in the repo's git common dir (default false). A dirty tree or an unpushed head isn't recorded; the review is still given. `finish.requireEvaluation` gates on it; `scope`: `full` (the default): review the whole branch every time. `delta`: with a recorded verdict, review only the files whose change moved since it; the record keeps the previous findings anchored in files it didn't review again, and its verdict is the new one, made worse only by those. When none moved (only the base was merged in), carry the verdict to the new head without a review. A recorded `stop`, or `evaluate full`, reviews everything again; `reviewer`: Who judges: `session` (the default), the session that runs evaluate, or `subagent`, a fresh subagent given only the gathered diff, the scope, the issue, the tests' result, and the scan's findings, never the conversation that wrote the code. When the subagent fails twice, evaluate says so, gives no verdict, and records nothing; `stopOn`: What records `stop`, the verdict finish never lets through: `rethink` (the default), only a Rethink; `high`, also any confirmed HIGH risk, or a confirmed scan finding whose first word is `STOP` (otherwise those record `flag`, which finish lets you accept); `instructions` [string[]]: Repo-relative files holding the repo's own review rules (a rubric, a checklist), pasted verbatim into the judging prompt, the subagent's too, as an extra lens: they add what to look for and how to grade it, and never change the report's format or the verdict rules; `tests`: Command that runs the tests relevant to the change before the judging, from the repo root; `{tests}` is the test files evaluate picks (shell-quoted), and with none it doesn't run. `{base}` and `{files}` as for `ready.fix`. Its output goes to a log in the git dir; the judge gets whether it passed and the log's path, and a failure is a finding, never the verdict by itself. Like a scan, it may write only the caches and build output a test runner keeps; `fetch` [boolean]: Fetch `origin/<base>` before diffing against it (default false: the remote-tracking ref as it is, with no network call); `scan` [hook[]]: Once evaluate has its scope, before it judges the change: the repo's own deterministic checks (a scan of the diff against its rules). What a passing command prints goes to the reviewer as findings to verify, each confirmed or set aside against the diff, never as the verdict. Commands only read: evaluate changes nothing, so they must not change the checkout or write anywhere. A failure stops the command. |  | Leave it out for evaluate's read-only review, a recommendation only. Set `record` when finish should gate on a verdict (with `finish.requireEvaluation`), `scope` to `delta` when branches are reviewed several times and a review of what moved is enough, `reviewer` to `subagent` when the session that wrote the code shouldn't grade it, `stopOn` to `high` when no HIGH risk should merge without the work changing, `instructions` for a review rubric the repo already keeps, `tests` for the command that runs the tests a change touches (often the same as `ready.tests`), `fetch` when the local copy of the base is often stale, and `scan` for a script the repo already runs over a diff against its own rules |
| `finish` | Merge |  | Whether finish closes the issue itself, and the repo's own steps before finish lands a branch, before its CI wait, and after, for checks and cleanup no integration covers | `issueOnMerge`: What happens to the pull request's issue when it merges. `close` (the default): sync links it with the issue tracker's closing form (`Fixes <ID>`) and finish's close-out moves it to done. `tracker`: the closing form, but finish leaves the issue to the tracker's own integration with the source-control host (one that moves it to a state of its own, like In QA). `leave`: the linking-only form (`Part of <ID>`) and no close-out, so merging leaves the issue's state alone; `requireAllChecks` [boolean]: Wait on every CI check, not only the ones the base requires, and refuse to merge while any failed or was cancelled (default false: the host decides which failures block). `ready.ignoreChecks` still leaves its checks out; `unresolvedThreads`: Unresolved review threads that stop a merge: `allow` (the default: only what the host's own rules block), `bots` (any automated reviewer's), or `all` (anyone's); `blockingReviewers` [string[]]: Logins whose unresolved review threads stop a merge, whatever `unresolvedThreads` says: for a repo where only one automated reviewer's threads should block (`github-advanced-security`, CodeQL's). A login matches a thread's first comment's author, case aside, with or without `[bot]`; `requireClean` [boolean]: Refuse to merge with uncommitted changes even when the branch has no pull request yet, before finish's own sync could commit them (default false: with no pull request, finish runs sync, which commits what's uncommitted); `ciTimeout` [number]: Minutes finish waits for CI on the commit it lands to settle (default 30); `watchDeploy` [boolean]: After the merge, watch the deployment of the commit it landed (through the `deployments` integrations) until it succeeds or fails, and report each step (default false); `deployTimeout` [number]: Minutes the deploy watch waits for the deployment to succeed or fail before reporting it still pending (default 30); `deployLogLines` [number]: When a watched deployment fails, the last this many lines of each failed step's log (through the source-control `checkLog` op) lead the report (unset: no log, only the steps and the deployment's link); `sync`: How finish syncs the branch before its CI wait: `full` (the default) runs the whole sync, which catches the branch up to its base and pushes; `remote` refreshes only the pull request and its issue, so finish pushes nothing, and a branch that's behind, conflicting, or has unpushed commits stops for the user to sync first. `remote` keeps the commit CI and a recorded review saw as the one that lands; `requireEvaluation`: Gate the merge on evaluate's recorded verdict (`evaluate.record`) for the commit that lands: `pass` merges only on a pass, and a flag needs the user's explicit go-ahead; `flag` merges on a pass or a flag. With no verdict, or one on an older commit, finish runs evaluate (recording its verdict) and gates on that; a `stop` stops the merge. With `evaluate.scope: delta`, a verdict carries to the head when the branch only took in its base; `before` [hook[]]: After finish's pre-flight gates pass, before it syncs, waits for CI, or merges anything. Commands may change the checkout, but not deploy, publish, migrate, or write to a shared service or database. A failure stops the command.; `beforeCi` [hook[]]: After finish has synced the branch and marked its pull request ready, before it waits for CI on the commit that lands: for a commit that must land with the merge (a changelog entry), which the hook makes and pushes, so CI runs on it. Commands may change and push the branch, but not deploy, publish, migrate, or write to any other shared service. A failure stops the command.; `after` [hook[]]: At the end of finish, merged or stopped, just before its report: teardown the repo does itself (a preview server, a database it manages). `on: merged` runs a hook whenever the pull request merged, even when what came after it (the deploy watch) failed. Commands may have side effects outside the checkout: that's what teardown is. A failure is reported, and the rest still run. |  | Leave it out when merging needs nothing of the repo's own. Set `requireAllChecks` when the team never merges past a failing check, required or not; `unresolvedThreads` to `bots` when an automated reviewer's open thread should block, or `blockingReviewers` when only some reviewers' should (CodeQL's `github-advanced-security`); `requireClean` when uncommitted work should never ride along with finish's own sync; `ciTimeout` when CI on the landing commit takes longer than 30 minutes; `watchDeploy` when merging to the base deploys, and a merge isn't done until that deploy is, with `deployTimeout` when the deploy can take longer than 30 minutes and `deployLogLines` when a failed step's log says more than its name; `sync` to `remote` when catching up shouldn't happen inside finish (a slow CI run, or a review gate on the head commit). Set `requireEvaluation` when nothing lands without a review of its head (with `evaluate.record`). Set `issueOnMerge` to `tracker` when the tracker's integration with the host moves the issue on merge, `leave` when merging shouldn't move it at all (the team does by hand), `after` for teardown done by hand after a merge today (with `on: success`), `before` for a check that must pass before anything lands, `beforeCi` for a commit that must land with the merge (a changelog entry) |
| `cancel` | Close hooks |  | The repo's own steps when cancel throws a branch's work away: a check before anything is deleted, and teardown of what the repo set up for the branch | `before` [hook[]]: After cancel's survey and gates, before it closes the pull request or deletes anything: a check that must pass before the branch's work is thrown away. Commands may change the checkout, but not deploy, publish, migrate, or write to a shared service or database. A failure stops the command.; `after` [hook[]]: At the end of cancel, finished or stopped, just before its report: teardown of what the repo set up for the branch itself (a database branch, dev servers, a marker that it's closed). Commands may have side effects outside the checkout: that's what teardown is. A failure is reported, and the rest still run. |  | Leave it out when abandoning a branch leaves nothing of the repo's own behind. Set `after` for what's torn down by hand today (a database branch, dev servers, a marker a worktree setup script reads), usually the same as `finish.after` |
| `preview` | Preview |  | How preview starts the repo's dev server and where it serves, so it can open what a branch changed in a browser | `command`: Command that starts the dev server from the repo root and keeps it running. Preview runs it in the background when this checkout has no server running, its output in a log in the worktree's git dir, and waits until it answers; `url`: Where the dev server serves, when it's always the same for everyone (the port the repo's dev script fixes, not one you picked on your machine). Leave it unset when each worktree gets its own port: preview reads the URL the server prints, or the port this checkout's server listens on. When it's set and another checkout's server holds it, preview says so rather than open the other checkout's work; `timeout` [number]: Seconds preview waits for a server it started to answer (default 120). It goes on running past that; `afterOpen` [hook[]]: Once preview has opened the page, before its report: for getting the person onto it (signing in as a test user, picking an account, setting the state it shows). The config is the team's: a test user every teammate can use, with any secret it needs read from the environment, never one person's own login. `{url}` is the page it opened. A prompt is a task in the browser that opened it, done only when this session can drive that browser; else preview tells the person what it asked. Commands may change the local dev server's own data (a test session, seeded rows), but not the checkout, since preview never edits it, and not deploy, publish, migrate, or write to a shared service or database. A failure is reported, and the rest still run. |  | Leave it out when the repo has no web app to preview. Detection proposes `command` from a root `dev` (else `start:dev`, `serve`, or a `start` that isn't a production server) script. Set it by hand for a monorepo whose app has its own (`bun run --cwd apps/web dev`), and set `url` when the server always serves the same address and prints none. Set `afterOpen` when a page needs a step before the person can see it, such as signing in as a test user |
| `hooks` | General hooks |  | The repo's own steps around every dev-flows command but configure; a flow's own steps are in its section (`ready`, `finish`) | `before` [hook[]]: At the start of every dev-flows command but configure, before its first step, once its mode is known. Commands may change the checkout, but not deploy, publish, migrate, or write to a shared service or database, since it runs before ready too. A failure stops the command.; `after` [hook[]]: At the end of every dev-flows command but configure, finished or stopped, just before its report, after the command's own `after` hooks. Commands may have side effects outside the checkout (a notification). {
```json
  "version": 5,
  "repo": { "baseBranch": "main" },
  "integrations": {
    "github": { "owner": "acme", "repo": "web" },
    "linear": { "teamKey": "ENG" }
  },
  "skipped": ["integrations.sentry"]
}
```

`version` is the file format, set by `write`. An older file is upgraded when it's read (version 1 called the integrations `services`, and version 2 had a `merge.closeIssue` boolean where `issueOnMerge` is now: true became `close`, false `leave`; version 3 called the `finish` and `cancel` sections `merge` and `close`), and the next `write` saves it in the current format. `skipped` lists integrations the team chose not to configure. Sections and fields this plugin doesn't know (from a newer plugin, or added by hand) are reported as warnings and kept as they are.

A field marked `[hook[]]` is a list of **hooks**: the repo's own steps at that point (`ready.before`, `finish.after`, or `hooks.before` and `hooks.after` around every command but configure). Each is an object: a unique `name` (lowercase letters, digits, `.`, `_`, `-`), then either `run` (a command from the repo root: exit 0 passes, exit 2 hands its stderr to the agent as a task, anything else fails; with an optional `fix` command run once before checking again, `timeout` in seconds, default 60, `recheck: true` to run it again once its task is done, and, at `evaluate.scan`, `findings`, a regex for the lines that go to the reviewer) or `prompt` (a task for the agent at that point). `paths` (globs), `flows` (at a general point, the flows it runs around), `modes` (the flow's modes, at a flow's own points, or the `flows`' modes at a general one), and `on` (`success` or `failure` at an `after` point, or `merged` at `finish.after` and `hooks.after`) narrow when it applies. Commands get `{base}`, `{branch}`, `{outcome}`, and what the flow knows (`{pr}`, `{prs}`, `{issue}`, `{result}`, `{merge}`, `{since}`, `{scope}`), and the same as `AGENT_FLOWS_*` variables. Detection never adds hooks: the hooks walk (below) offers what the checkout suggests and adds only what the user takes, each in the section of the flow it's for, with that section's other fields in the write, since a write replaces the whole section.

A field marked `[project[]]` lists an issue tracker's **other projects**, beside its default `project`: each a name, or `{ "name", "paths" }` with globs for the changes that belong to it. Flows match a project a person names against them first and look for duplicates across all of them, and sync files a branch's new issue in the one whose paths the branch's changes match most (the default `project` when none match). Look the names up with the tracker's lookup, and ask which ones the repo's work goes in and which is the default; suggest `paths` only for a project the checkout plainly has a directory for (`apps/mobile` for Mobile), and confirm them.

A run goes one of three ways ($ARGUMENTS):

- **Auto** (`/dev-flows:configure auto`): examine this checkout and machine, settle everything that has one clear answer, and ask only about what's ambiguous.
- **Manual** (`/dev-flows:configure manual`): go through every section one at a time, skipped ones included, and ask about each.
- **Per section** (`/dev-flows:configure linear vercel`): the manual walk, for just the named sections. A name is a section path or its last part (`integrations.linear` or `linear`), or a capability (`issueTracker`), which stands for every integration that provides it. Only the named sections are detected, shown, and changed, even ones that were skipped or are already configured; the rest of the file stays as it is.

With neither a mode nor names, configure asks which mode to run.

Each integration also records what the team **uses** it for, under `use`: per capability it provides, a level from the table above (`"use": {"issueTracker": "track"}`), or `true` for a capability without levels. A capability left out isn't used, even if the integration provides it (PostHog only for feature flags). Flows never go past the level, so this is where a team decides, say, that sync links issues but doesn't file them. Without `use`, flows assume each capability's default level, and configure asks.

An integration can be reached in up to three ways: its **MCP server**, its **CLI**, or its **HTTP API** directly, with a token from an environment variable. Which ones work depends on the machine, not the repo, so it's never written to the config: every flow checks at run time and uses the first that works, in that order. When that way fails on the way in (an MCP server that errors or wants a sign-in, a CLI that's signed out, an API that rejects the token or is down), the flow falls back to the next, so a second way is a backup, not just an alternative. Configure uses the same check to offer integrations this machine can already reach, even when the repo shows no sign of them.

**A local override** is for a repo whose config isn't yours to change (someone else's), or settings only you want: `/dev-flows:configure local` (with a mode or sections as usual) writes to this machine's override instead of `.agent-flows/config.json`. It lives in the repo's git dir, so the repo's worktrees share it and it can never be committed. It's the same format, and applies one of two ways, recorded in the file as `"override"`:

- **Merge** (the default): each section it sets is laid over the committed one field by field, so it can hold just one personal field (an integration's `agent`) and keep the team's others (a section configured as a list is replaced whole), and each it skips is dropped; the rest follows the committed file as the team changes it. A repo with no config at all can be configured entirely this way.
- **Replace** (`/dev-flows:configure replace`): the override is the whole config and the committed file is ignored. Switching to it starts from the config as it reads now, so nothing is lost, but later changes to the committed file no longer reach this machine.

Re-running is safe: values already in the file are kept, skipped sections stay skipped (until a manual run or naming them brings them back), and when nothing new turns up the command says so and changes nothing.

**CLI commands** available via Bash (paths relative to `${CLAUDE_PLUGIN_ROOT}/src/commands/`):

| Command | Description |
|---------|-------------|
| `configure.ts <subcommand>` | `show` the config, `detect [auto|manual]` what this checkout uses and plan changes, `get <path>...` values, `integrations <capability>...` for a capability's configured integrations, `write [--local [--merge|--replace]]` a patch read from stdin (JSON), to the committed config or this machine's override, or `token <integration> --env|--file|--command <where>` to record where an API token is on this machine |

## Invariants

- Never write a token, key, password, or connection string into the config, and never read a real `.env` file to find one. If the user pastes a secret, don't save it, and tell them it doesn't belong in this file.
- The committed file is the team's, so it holds only what's the same for everyone on it: never a value that's only true for you or this machine (an absolute path, a local port, your own user or account id, an id a local app made when you added the repo to it). Such a value goes in the local override (`/dev-flows:configure local`), or is left out for flows to work out where they run.
- Never call a service in a way that changes it. Lookups are read-only, and that includes local setup: don't run a CLI command that initializes or configures the tool in this repo (some do on first use), even to read a value. Read its files instead, or ask.
- Only change the config through `write`; never edit the file by hand to get past the validator.

## 1. Pick the mode

If the user typed `local` or `replace`, or asked for a configuration only they use (it's someone else's repo, or they don't want to change the team's file), this run writes to the local override: carry the word through to detect (`replace` when they want to ignore the committed config entirely rather than layer over it). If the user typed `auto`, `manual`, or any section names, that settles it: go straight to detect. Otherwise use `AskUserQuestion` how to run it:

> A) **Auto**: examine the repo and this machine, and ask only about what's ambiguous *(recommended)* → step 2
> B) **Manual**: go through every section, one at a time → step 2

## 2. Detect

```bash
node "${CLAUDE_PLUGIN_ROOT}/src/commands/configure.ts" detect [auto | manual] [local | replace] [section | capability ...]
```

Pass the mode (typed or picked), `local` or `replace` for a local run, and the sections or capabilities the user named, if any, as they typed them. An unknown name fails with the list of known sections, capabilities, and modes: show it and ask which they meant.

The JSON has `mode` (`auto` or `manual`; names alone mean `manual`), `local` (true for a local run) and `replace` (true when it should replace the committed config), `configPath`, `exists`, `localPath`, `override` (`merge` or `replace`), and `overridden` (when this machine has an override: its file, how it applies, and, merged, the sections it sets or skips), the current `config` (when valid, with the override applied), its `issues`, `requested` (when you passed names: the section paths they resolved to, with each capability expanded to its integrations), `coverage` (per capability, the integrations configured for it), `detected` (per section path: guessed `values` and the `evidence` behind them, from local files and git metadata only), `hookSuggestions` (hooks the checkout suggests, not already configured: each with its `point`, the `hook`, and the `evidence`, which says what to check before taking it; offered in the hooks walk, never planned), and a `plan`:

- `changes`: sections to `add`, and empty fields of configured sections to `fill`.
- `needs`: required fields still missing after those changes (per instance, with its `instance` name, for a list).
- `conflicts`: configured values that disagree with detection. Configured values always win; mention a conflict, never change it on your own.
- `moreInstances`: for an integration that's already configured, instances detected that match none of its configured ones (a second linked Vercel app). Detection only fills the instance it matches, and never edits a list. These are offered, not planned, and don't make the config out of date.
- With `requested` set (the named sections, or every section in manual mode), the plan covers only those sections, and proposes each even if it was skipped or nothing was detected, plus any section marked *always* that the config still lacks (the file isn't valid without it).
- `upToDate`: the config exists and there is nothing to add or fill. Sections listed in `skipped` were deliberately left out on an earlier run and are never proposed again.

`access` says, per integration, how this machine can reach it: `cli` (`installed`, and `ready` when it's also signed in), `api` (the token variable, and `ready` when it's set; never print its value), and `mcp.server`, which only you can check: it's available when your tools include ones from that MCP server (named for it, like `mcp__<server>__…`, or a connector of that name). An integration is **in reach** when it isn't configured, isn't in `skipped`, and one of those three works.

Route on the result:

- **`issues` is non-empty (the file is broken)**: show the issues and stop. For each issue, say what's wrong and the fix (a wrong type or a missing required field); with the user's OK, fix it with `write`, or by hand only when `write` refuses because the file is unreadable, then re-run this command. A version newer than the plugin means the user should upgrade the plugin instead
- **`mode` is `auto`, `plan.upToDate` is true, and no integration is in reach**: say the config is already up to date (any `warnings` and any `conflicts` too) and change nothing. If `plan.moreInstances` isn't empty, add one line per integration naming the instances found, and that `/dev-flows:configure <integration>` adds them → step 6
- **`mode` is `manual`**: walk the `requested` sections one at a time → step 3
- **otherwise (`auto`)**: continue → step 3

## 3. Fill the gaps

How much this step asks depends on the mode.

**Auto: ask only what's ambiguous.** Settle everything with one clear answer yourself, and keep the questions below for real choices:

- Integrations in reach that the plan doesn't add: don't ask about them, and don't skip them. List them in confirm as available but not added, so `/dev-flows:configure manual` or `/dev-flows:configure <integration>` can pick them up later.
- `use`: record each capability's default level without asking, and leave out `(opt-in)` capabilities. Ask only when the repo points somewhere else (its agent instructions say sync files issues, an opt-in capability no other integration covers).
- Tokens: when an integration's usual variable is already set (`access.api.ready`), the token is found; don't ask. Ask only when one is needed and none is found.
- Lookups: a lookup with exactly one result is the answer. Ask when it returns several (two Vercel projects, several Linear teams) or none.
- Several integrations detected for one capability, `plan.conflicts`, and `plan.moreInstances`: ask.
- A section that can't be filled without the user and isn't worth asking about: leave it out of this run rather than skipping it.
- `ready`: a detected `fix` and `checks` is one clear answer: take it without asking. When its `evidence` names other candidate scripts ("also has a … script"), ask which one ready runs.
- Hooks: never add any. When `hookSuggestions` has some, list them in confirm as available, with `/dev-flows:configure hooks` (or `ready`, `finish`) to set them up.

**Manual: one section at a time.** Go through the `requested` sections in the sections table's order. For each, show what's configured (and any of its `plan.moreInstances`), what was detected, and how this machine reaches it, then use `AskUserQuestion` whether to configure it, keep it as it is, or skip it, then ask the questions below for that section only before moving on. Recommend keeping what's configured, and configuring what was detected or is in reach.

The rest of this step applies to both modes, within those limits.

**Offer what's in reach.** Auto only lists these (above), and naming sections leaves them out. In manual mode with no names, take the integrations in reach that the plan doesn't already add, and use `AskUserQuestion` with multiple selection: which of them should the repo use? One option per integration, saying how it's reached (`Linear: MCP connected`, `Vercel: CLI signed in`, `Sentry: SENTRY_AUTH_TOKEN set`). Being reachable from this machine doesn't mean the repo uses it, so recommend none by default, only ones the repo shows signs of. With more than fit in one question, ask several. The ones picked join the plan as sections to add; the rest go in the write's `skip` list, so the next run doesn't offer them again.

**Ask what each is for.** For every integration being added, and every configured one `plan.needs` lists `use` for, use `AskUserQuestion` what the team uses it for: one question per capability it provides, with that capability's levels from the table above plus "Not for this", and its default level recommended. For a capability the sections table marks `(opt-in)`, recommend "Not for this" unless the repo shows it uses the integration for it (no other integration covers the capability, and the agent instructions or recent PRs point to it), since without `use` flows leave it out. An opt-in `stacking` (stacks of plain pull requests, each based on the branch below it) is the exception worth raising: recommend it when no other stacking integration is configured or detected and the repo's open pull requests include ones whose base isn't the base branch (a read-only list of them, such as `gh pr list --state open --json headRefName,baseRefName`), and never next to another stacking integration, which is preferred when there is one: the config refuses two.A capability without levels is a yes or no. Several integrations can go in one call, up to its limit on questions. Record the answers as the entry's `use`, and leave out the capabilities answered "Not for this". If every capability is "Not for this", the integration isn't used: skip it instead.

**Ask where each token is.** For every integration being added or already configured that has an API, ask where its API token is on this machine when `access.api.configured` is false and either the table lists adapters for it (they need the token) or neither its MCP server nor its CLI works here. Don't look for the token yourself (no searching the disk, no reading files or variables to see what's there); the user says where it is. use `AskUserQuestion` with the options:

- **An environment variable**: its name (the integration's usual ones, from the table, are a good default).
- **A file**: the path of a file holding just the token.
- **A command**: one that prints it, like a password manager's (`op read op://<vault>/<item>/credential`).
- **None**: use its MCP server or CLI instead; adapters that need the token are skipped.

Record each answer: `node "${CLAUDE_PLUGIN_ROOT}/src/commands/configure.ts" token <integration> --env <NAME>` (or `--file <path>`, `--command '<command>'`; `--clear` forgets it). It saves where the token is, never the token, in the repo's git dir: per machine, shared by the repo's worktrees, never committed, and not part of the confirm table below. Never print a token, and never pass one to the command. An integration configured more than once on separate accounts (a second Linear workspace, searched read-only) needs a token per account: ask for each instance, and record it as `token <integration>:<instance>`; an instance without its own uses the integration's.

Then work through `plan.changes` and `plan.needs` (other than `use`), plus the sections picked or named. Evidence that a service is used (a dependency) is not the same as its ids, so look up each missing required field read-only, in this order:

1. **The section's lookup** from the table above, through whichever way of reaching it works here: its MCP server, its signed-in CLI, or its API with the token variable (never print the token).
2. **The user**, for anything still missing or ambiguous (two Vercel projects, several Linear teams).

When detection finds several instances of one integration (`detected.<path>.instances`, like a linked Vercel project per app), the plan proposes them all as a list: confirm each, and drop the ones the team doesn't want. To add instances to an integration configured as a single object (the user asked, or accepted some of `plan.moreInstances`), turn its entry into a list: give the existing one a `name` and add the new ones. Names are unique within the list and use lowercase letters, digits, `.`, `_`, and `-` (`web`, `apps-docs`).

Several integrations can provide the same capability (Linear and Jira are both issue trackers). Don't make the user pick just one: when detection finds evidence for more than one, propose each, and when the user named a capability, ask which of its integrations the team uses. They can choose any number; configure those and skip the rest.

**The hooks walk.** For each `requested` section with hook fields (`hooks`, `ready`, `finish`, `cancel`; in manual mode, once the user chooses to configure it), go through its points in order: `hooks`: `before`, `after`; `ready`: `before`, `beforePublish`, `beforePush`, `beforeFixPush`, `after`; `finish`: `before`, `beforeCi`, `after`; `cancel`: `before`, `after`. For each point:

1. Say in one line when it runs and what it may do (its field's description in the sections table), and list the hooks it has now.
2. ## 5. Write

For a local run, add `--local` (`node "${CLAUDE_PLUGIN_ROOT}/src/commands/configure.ts" write --local`): the patch then applies to this machine's override, `null` removes a section from the override so the committed one applies again, and `skip` drops a committed section for this machine only. When detect said `replace`, add `--replace` too: the override then becomes the whole config, starting from the config as it reads now, with the patch on top. To go back to layering over the committed file, add `--merge`. Either one is remembered in the file, so later local writes need only `--local`, and with no changes to make, `echo '{}' | node "${CLAUDE_PLUGIN_ROOT}/src/commands/configure.ts" write --local --replace` just switches. Otherwise it writes `.agent-flows/config.json`.

Pass only what changes on stdin, keyed by section path. Each section you include **replaces** that section's whole entry (so include its existing fields too: filling `ready`'s `fix` and `checks` keeps its `skip`, `ignoreChecks`, and hooks); `null` removes one; `skip` marks sections as deliberately not configured; everything you omit stays as it is.

```bash
node "${CLAUDE_PLUGIN_ROOT}/src/commands/configure.ts" write <<'JSON'
{"sections": {"repo": {"baseBranch": "main"}, "integrations.github": {"owner": "acme", "repo": "web"}, "integrations.linear": {"teamKey": "ENG"}}, "skip": ["integrations.sentry"]}
JSON
```

A list entry replaces the whole list, so include every instance you're keeping: `"integrations.vercel": [{"name": "web", ...}, {"name": "docs", ...}]`.

It validates the whole result and writes only if the content changed (a different layout or key order doesn't count), with sections in a fixed order, so the same answers always produce the same config. It then lays the file out with the repo's own Biome or Prettier, when one is installed, so the next lint fix leaves it alone: `"formatted"` names the formatter, or is `false` with a `formatReason`. On issues it prints them with `"written": false` and exits 1: fix each one and run it again. `warnings` (unknown sections or fields it kept) are worth mentioning but don't block.
